# ADR-0010：剪贴板历史的存储方案

- 状态：已采纳
- 日期：2026-11-03

## 背景

M2 剪贴板要长期保存历史：文字、富文本、图片、文件路径。用户的要求：
- 默认上限 2 GB，可以设为永久保留；
- 能查看占用；
- 能删除最旧的 N MB，或者某个日期之前的条目。

条目可能上万条，需要全文搜索。不能引入第三方依赖。

## 决定

- **元数据和小数据放 SQLite**：用系统自带的 libsqlite3（`import SQLite3`，系统库，不算第三方依赖），开启 WAL 模式。
  - 文件位置：`data/clipboard/history.sqlite`。
  - 表 `clip`：类型、摘要、来源 App、时间、字节数、是否固定、内容哈希（用于去重）。
  - 表 `clip_data`：每个剪贴板类型（UTI）一行。不超过 64 KB 的内容直接存在这里，更大的（主要是图片）存文件 `data/clipboard/blobs/<sha256>`，表里只记路径。
  - 表 `clip_fts`：FTS5 全文搜索，内容是条目的文字。系统 SQLite 已开启 FTS5（2026-11 实测）。
- **原样保存所有类型**：粘贴时把同一个条目的所有类型（例如 HTML、RTF、纯文本）都写回剪贴板，目标 App 自己挑最合适的格式。
- **文件只记录路径**（与 Ditto 相同），不复制文件内容，不计入占用。
- **大小统计以 `clip.byteSize` 为准**：它等于该条目所有类型的数据之和。删除条目时同时删掉对应的 blob 文件；大文件独立存放，删除后空间立即释放，不依赖 VACUUM。
- **清理规则是纯函数**（`Domain/RetentionPolicy`）：固定的条目永远不被自动清理。
- **密码等内容不过滤**（用户明确要求：纯本地使用，没有保密需求）。只忽略一种情况：MAIO 自己恢复剪贴板时写入的内容，以 `org.nspasteboard.RestoredType` 标记。

## 备选方案

- **SwiftData / Core Data**：做 FTS 和按大小批量删除都不方便，迁移也不透明。
- **全部存 JSON 文件**：上万条时无法高效搜索和增量更新。
- **把图片也存进 SQLite**：数据库文件只增不减，删除后要靠 VACUUM 才能释放空间，2 GB 的库做一次很慢。

## 后果

- 功能内部有一层很薄的 SQLite 封装（`Infrastructure/SQLite.swift`），只服务于剪贴板，不放进 MAIOKit。
- 以后其他功能也需要数据库时，再考虑把这层封装提升为 MAIOKit 服务（需要另写 ADR）。
