# ADR-0014：长截图用"分竖条行哈希 + 最长连续匹配段"计算偏移，不用 Vision 配准

- 状态：已采纳
- 日期：2026-11-03
- 关联：ADR-0011（截图流程）、spec M5 第 4.6 节

## 背景
spec 4.6 要求实现长截图前，先比较两种偏移算法：行哈希加容差，以及 Vision 的 `VNTranslationalImageRegistrationRequest`。

实验方法：用离屏 WKWebView 加载真实网页，用 JS 按已知距离滚动，每次取快照。真实偏移等于 `scrollY` 之差乘以缩放倍数。测试数据共 9 组 106 对帧：

- 页面：Wikipedia、MDN（有吸顶栏，左侧目录栏固定且高亮项会变）、GitHub、Apple 开发者文档（吸顶栏是半透明毛玻璃，下面的内容会透出来）；
- 缩放：1x 和 2x；
- 步长：37 到 500 CSS px 不等。

实验脚本在 `/tmp/maio-exp/longshot/`，没有提交。

## 结果

| 算法 | 正确 | 每帧耗时（Release） |
|---|---|---|
| Vision 平移配准 | 98/106 | 11–41 ms |
| 整行哈希 + 匹配率阈值（第一版） | MDN 只对一半 | 2–10 ms |
| 分 16 条竖条 + 每条取最长连续匹配段之和（最终方案） | 104/106 | 5–26 ms |
| 最终方案 + 自动滚动的预期位移 | 105/106 | 16 ms 平均 |

**Vision 的问题**：两帧重叠少时会算错（例如真实是 1000 算成 624），偶尔给出离谱值（−963、−458）。它也不报告吸顶栏、页脚这类固定区域，而拼接需要这些信息。

**整行比较的问题**：
- 侧栏高亮项变化后整行都对不上；
- 毛玻璃吸顶栏的行在任何位移下都对不上，会拉低匹配率。

改成"每个竖条单独找最长连续匹配段"后，局部变化只会打断一小段，不影响最长段。

剩下的两个错误：
- 一例是页面在两帧之间重新排版（演示区域加载完，下面的内容多移了 14 px）。用自动滚动的预期位移纠正：置信度低时，在预期值附近、得分不低于最佳 60% 的候选里取最近的。
- 另一例在 1x 下只差 1 px，是亚像素渲染差异，可以接受。

逐像素比较是可行的：WebKit 和 AppKit 在整数像素位移下，同样的内容逐像素完全一致。

## 决定
- 采用 `Domain/ScrollMatcher`：
  1. 排除两帧之间不变的列（固定侧栏）和左右边缘（滚动条）；
  2. 每行切成 16 个竖条分别哈希，空白格子不参与；
  3. 首尾整行相同的部分作为固定区域（吸顶栏、页脚）；
  4. 对每个候选位移，把各竖条的最长连续匹配段长度加起来作为得分，取得分最高的位移；置信度为 1 − 次佳得分 / 最佳得分。
- 采用 `Domain/StitchPlan`：只记录每一帧贡献哪几行；页脚只保留最后一帧的，吸顶栏只保留第一帧的。
- 内存控制：每帧只把需要的行复制成小图（`cropping` 会持有整帧的数据），最后一次性合成。内存约等于最终长图的大小。spec 原本计划把帧写进临时文件，现在没有必要。
- 截图方式：用 `SCContentFilter` 排除 MAIO 自己的窗口，所以边框和提示条放在选区里也不会被截进去。第一帧也用同样方式截取，不用冻结画面，因为两种截图方式的颜色处理可能有细微差别，会让逐像素比较失败。
- 自动滚动：
  - 每次滚动选区高度的 40%，等 260 ms 后再截图；
  - 合成滚轮事件发到鼠标所在位置，所以开始时如果鼠标不在选区内，会先把它移到选区中心；
  - 不修改 `MAIOKit`：沿用已有的 `SyntheticEvent.scroll`。

## 后果
- 改变自身布局的页面（懒加载、动画）只能尽量处理；无法避免时，拼接处可能出现错位。
- 滚到底的判断是连续 3 帧没有变化。如果选区里有持续的动画，到底后会一直判定为"对不上"，也会在 3 帧后停止。
- 长截图期间通过键盘会话接收 Esc 和 ⏎，期间的按键都会被吞掉，不会传给下面的 App。

## 修订（2026-11-03，同日）：改为手动滚动，加长条预览，提速
- 用户要求：**只用手动滚轮往下滚，不要任何自动滚动**；选区右侧显示长条预览。去掉了合成滚轮事件、把鼠标移到选区中心、"连续 3 帧不动自动结束"。现在只能手动结束（完成按钮、Esc、⏎）或达到 30000 px。
- 手动滚动要求连续截帧，算偏移要快。MAIO 平时运行的是 Debug 构建，原实现在 Debug 下每帧 2 秒。改进：
  - 先投票：竖条哈希相同的格子给"行号之差"投票，只对得票最多的 12 个位移完整打分；
  - 隔列抽样；
  - 平铺数组 + 指针遍历。

  改进后 Debug 52 ms/帧、Release 3 ms/帧，准确度不变（105/106）。另测了 1～150 CSS px 的小位移（模拟手动滚动）32 对，全部正确。
- 最低得分改为 `max(20, 竖条数 × 4)`：隔列抽样后，低信息量内容的偶然匹配变多，原来的固定阈值 20 不够。
- 预览：`LongImageBuilder` 每加一段同时保存一份缩小版（宽 360 px），合成预览只用缩小版，代价很小。

## 修订二（2026-11-03）：用户实测失误率高，参考 Snow Shot 重做匹配与拼接
用户在 GitHub 仓库页实测，README 的整块内容被重复拼接。复现（`/tmp/maio-exp/longshot/dym`，仿手动滚动的不规则步长）后找到原因：
- **竖线和重复元素**：卡片的竖直边框在每一行都一样，在任何位移下都能"匹配"，连成整屏长的连续段。于是两帧完全没有重叠（真实位移 1500 px）时，也给出了"位移 32、置信度 0.66"的错误匹配。
- **空白被当成固定区域**：首尾整行相同就算吸顶栏或页脚，大片空白也会被算进去，挤掉可搜索的位移范围。

参考了 Snow Shot（`references/snow-apps`，ORB 特征 + 严格验收 + 画布覆盖式拼接）和 eSearch（FFT 相位相关，但不检查置信度，快速滚动必错），只借鉴思路，用自己的行哈希实现：

1. **证据**：一个格子要满足三个条件才算证据——有内容、哈希在上一帧同一竖条里最多出现 2 次（排除竖线、分隔线）、和上一帧同一位置不同（"没动"的吸顶栏、页脚、侧栏自然排除，相当于 Snow Shot 的"位移 0 候选"）。
2. **验收**：以下全部满足才接上，否则这一帧作废、参照帧不前进；滚回去有重叠时自然接上：
   - 位移 ≤ 画面高度的 70%；
   - 得分 ≥ max(20, 竖条数 × 4)；
   - 至少 4 个竖条有匹配；
   - 重叠区证据的匹配比例 ≥ 50%（实验中正确的 ≥ 0.64，错误候选 ≤ 0.25）；
   - 和次佳位移的差距 ≥ 0.15。
3. **拼接**：不再检测吸顶栏和页脚。新帧滚动 shift 行时，取它最后 max(H/2, H/4 + shift) 行覆盖画布末尾。画布末尾永远是最新一帧，所以页脚只在最后出现，吸顶栏不重复。
4. **取帧**：改用 ScreenCaptureKit 视频流（`RegionStream`，最高 60 fps，只要内容完整的帧，只保留最新一帧）。
5. **往回滚**：往下对不上时，把两帧反过来再比一次；能对上就说明在往回滚，暂时不拼、不报错。

结果（仿真流水线，参照帧只在接上时前进）：
- 12 组数据 156 次比较：**错误拼接 0**，原来至少 1 次；
- 位移在上限以内却没接上的只有 3 种情况：页面在两帧之间自己变了（吸顶栏出现、演示区重新排版），以及 1x 下的大位移；
- Debug 构建每帧 63 ms。

用户的 GitHub 页面前 10 帧拼出来的图没有重复，也没有缺失。

合成数据测试：每个格子只有 4 列、2 级灰度时，区分度太低（所有格子都"重复"）。真实截图每个格子有 30 多列、256 级灰度，所以测试的合成文档改成了随机灰度。

## 修订三（2026-11-04）：用户反馈仍经常失效/错误，重做匹配与拼接

用户实测仍"经常失效或者错误"。原方案最脆弱的假设是
**"整数像素位移下逐像素完全相等"**：真实触控板惯性滚动是浮点偏移，合成器会重采样，
加上动画、光标、毛玻璃，一个格子 30 多列里变一个像素，整格哈希就废了；再叠加"候选只取
哈希投票前 12 名"和较高的置信度门槛，正确位移经常根本进不了打分。
（分析过程记录在本地 `docs/notes/`，不随开源仓库发布。）

改成参考成熟滚动拼接实现的**像素域容差匹配**：

1. **容差**：两帧像素差 > 10 才算"变了"/"对不上"。不再要求哈希完全相等。
2. **证据是像素而不是格子**：只有"同一位置两帧不同"的像素参与比较。固定吸顶栏、侧栏、
   空白既不算证据，也不会拉低匹配率（之前按整行判定，固定侧栏会被拖进来，正确位移反而被拒）。
3. **全偏移搜索**（±70% 画面高度），不再依赖哈希投票的前几名。
4. **分层**：先按列抽样到 ≤ 512（高度不变，保证 1 像素精度），再块平均到 64×128 做全偏移粗搜；
   粗搜取 4 个候选，回到精层在候选 ±(scale+2) 行内逐像素细化。
5. **验收**：最佳位移的不匹配率 ≤ 30%，且次佳（相差 3 行以上）必须差 0.03 以上；分不清就
   返回 `unknown`，参照帧不前进。
6. **往回滚**：搜索直接覆盖负位移，一次就能识别；只要匹配成功（包括往回滚、落在已拼范围内）
   就更新参照帧和位置，所以"滚回去再往下滚"能立刻恢复，不再需要"反向再比一次"。
7. **拼接**（`StitchPlan`）：显式维护"当前画面顶部在画布中的位置"，按绝对位置写入。
   往下滚写新帧靠下的一段（band = max(H/2, H/4+shift)），往回滚落在已拼范围内只更新位置，
   超过起点时画布整体下移、由该帧的上半帧补上头部。多帧覆盖后页脚只在最后出现，
   吸顶栏不会被写进画布中间。
8. **节奏**：每处理一帧至少间隔 30 ms；视频流里积压的中间帧本来就会被丢掉。
   Debug 构建 1440×900 实测约 80 ms/帧（原来 63 ms），Release 未实测。

测试：`ScrollStitchTests` 改为覆盖小位移（1～205 px 精确到 1 px）、往回滚（负位移）、
±6 灰度噪声、吸顶栏/页脚/侧栏、重复分隔线、往回滚后再往下滚的连续性。
